01 / 推荐
通过 GitHub 绑定自动部署无需本地环境 · Cloudflare Dashboard
前置要求

准备一个 Cloudflare 账号，并启用支持 TCP Sockets 与 Durable Objects 的 Workers 计划。CloudSSH 的 SSH 会话与用户数据依赖这两项能力。

  1. Fork 仓库

    点击上方 Fork CloudSSH，将仓库复制到自己的 GitHub 账号。

  2. 创建 Worker 应用

    登录 Cloudflare Dashboard，进入 Workers & Pages → Create application，连接 GitHub 并选择刚刚 Fork 的仓库。

  3. 填写构建配置

    Production branch 设为 main，Build command 填写：

    pnpm run build:frontend
  4. 保存并部署

    等待首次构建完成，然后通过默认地址 https://cloudssh.<你的子域>.workers.dev 访问。

  5. 绑定域名（可选）

    进入 Worker 的 Settings → Domains & Routes → Add，添加自己的域名并等待证书生效。

PRODUCTIONcloudssh

main 分支 · 正式域名 · 生产数据

TESTcloudssh-test

test 分支 · 测试域名 · 独立数据

双环境提示：为 test 分支再创建一个独立 Worker。两个 Worker 即使绑定相同的 Durable Object class_name，数据仍完全隔离。

02 / 可选
让 Fork 自动同步上游版本每天 04:20 检查 · 也可手动触发

项目内置 Sync upstream GitHub Actions 工作流，默认关闭。启用后，Fork 的 main 更新会触发 Cloudflare Git 集成自动构建。

  1. 确认部署连接

    Cloudflare Worker 应连接你自己的 Fork，Production branch 为 main，自动构建保持开启。

  2. 启用 Actions

    进入 Fork 的 Actions 页面启用工作流。较早的 Fork 若没有该工作流，先使用 GitHub 的 Sync fork 同步一次。

  3. 开启定时同步

    前往 Settings → Secrets and variables → Actions → Variables，创建 Repository variable：

    AUTO_SYNC_UPSTREAM=true
  4. 立即同步（可选）

    进入 Actions → Sync upstream → Run workflow 手动执行；手动执行不要求设置上面的变量。

同步边界：工作流使用 GitHub Fork 同步接口，不需要 PAT，也不会强制覆盖分支。若 main 与上游冲突，任务会失败并保留你的代码；需要手动解决冲突。域名、密钥和环境变量应保存在 Cloudflare Dashboard，不要提交进仓库。

03 / CLI
使用 Wrangler 本地部署适合开发、调试与可控发布
  1. 克隆仓库
    git clone https://github.com/newbietan/CloudSSH.git
cd CloudSSH
  2. 安装根目录和前端依赖
    npm install -g pnpm
pnpm install
cd frontend && pnpm install
cd ..
  3. 授权 Wrangler
    npx wrangler login
  4. 部署正式环境
    pnpm run deploy
  5. 部署隔离测试环境（可选）
    pnpm run deploy:test

04 / 安全
配置 Cloudflare Turnstile阻止机器人滥用匿名连接
  1. 创建 Widget

    在 Cloudflare Dashboard 的 Turnstile 页面创建 Widget，并添加实际访问域名。

  2. 保存两把密钥

    记录公开的 Site Key 与保密的 Secret Key。

  3. 写入 Worker 配置

    进入 Worker → Settings → Variables and Secrets，添加：

    TURNSTILE_SITEKEY = Site KeyTURNSTILE_SECRET = Secret Key
  4. 重新部署

    重新部署当前 Worker，使配置进入新版本。

类型建议：变量建议统一设为 Secret 类型。Turnstile 验证按浏览器会话生效，关闭浏览器后需要重新验证。

05 / 账号
配置 GitHub OAuth 与服务器管理可选登录 · 匿名 SSH 仍可使用
  1. 创建 OAuth App

    进入 GitHub Settings → Developer settings → OAuth Apps → New OAuth App，填写：

    Application name = CloudSSHHomepage URL = https://your-domain.comCallback URL = https://your-domain.com/api/auth/callback
  2. 保存 GitHub 密钥

    记录 Client ID，生成 Client Secret 并立即保存——Secret 只完整显示一次。

  3. 写入 Worker 配置

    在 Settings → Variables and Secrets 添加：

    GITHUB_CLIENT_ID = Client IDGITHUB_CLIENT_SECRET = Client SecretBASE_URL = https://your-domain.com
  4. 重新部署并验证

    部署后登录入口会自动出现；未配置 OAuth 时入口自动隐藏，不影响匿名连接。

凭据边界：保存的密码或私钥在每个用户的 UserDBDO SQLite 中使用 AES-256-GCM 加密。一键连接时浏览器不会收到明文凭据，服务端以一次性令牌完成内部传递。

06 / 必读
Secrets、域名与迁移注意事项升级已有环境前请确认
Secrets

Dashboard 路径：Worker → Settings → Variables and Secrets。CLI 可使用：

npx wrangler secret set <SECRET_NAME>
自定义域名

在 Settings → Domains & Routes 分别为 production 与 test 绑定域名。开源仓库的 wrangler.toml 不硬编码个人域名。

BASE_URL

启用 OAuth 时必须与用户实际访问的协议和域名完全一致，否则回调校验会失败。

Durable Object 迁移

新增 DO 类必须使用新的、不可复用的 migration tag。正常升级不要删除 Worker；只有确认没有数据需要保留且明确重建环境时才删除。

发布前检查

确认生产连接 main，测试连接 test；两个环境使用不同 Worker 名称与域名。先在测试环境验证登录、SSH、SFTP 和迁移，再发布生产环境。

01 / RECOMMENDED
Deploy through GitHub integrationNo local setup · Cloudflare Dashboard
Prerequisites

Use a Cloudflare account with a Workers plan that supports TCP Sockets and Durable Objects. CloudSSH relies on both for SSH sessions and user data.

  1. Fork the repository

    Use the Fork CloudSSH button above to copy the project into your GitHub account.

  2. Create a Worker

    Open Cloudflare Dashboard, go to Workers & Pages → Create application, connect GitHub, and select your fork.

  3. Set the build

    Choose main as the production branch and use:

    pnpm run build:frontend
  4. Deploy and visit

    After the first build, open https://cloudssh.<your-subdomain>.workers.dev.

  5. Bind a domain (optional)

    Open Settings → Domains & Routes → Add, add your domain, and wait for the certificate.

PRODUCTIONcloudssh

main · production domain · production data

TESTcloudssh-test

test · test domain · isolated data

Two environments: create a separate Worker for test. Durable Object data remains fully isolated even when both Workers bind the same class_name.

02 / OPTIONAL
Keep a fork synchronized upstreamDaily 04:20 CST check · manual trigger available

The built-in Sync upstream GitHub Actions workflow is disabled by default. Once enabled, main-branch updates in the fork trigger Cloudflare's Git deployment.

  1. Check the deployment link

    The Worker must use your fork, main as production, and automatic builds.

  2. Enable Actions

    Enable workflows on the fork. Older forks should first use GitHub's Sync fork if the workflow is missing.

  3. Enable scheduled sync

    Under Settings → Secrets and variables → Actions → Variables, create:

    AUTO_SYNC_UPSTREAM=true
  4. Sync immediately

    Run Actions → Sync upstream → Run workflow. Manual runs do not require the variable.

Sync boundary: the workflow uses GitHub's fork sync API, needs no PAT, and never force-overwrites conflicts. A conflict fails safely and keeps your code. Store domains, keys, and environment values in Cloudflare Dashboard—not in Git.

05 / IDENTITY
Configure GitHub OAuth and saved serversOptional sign-in · anonymous SSH stays available
  1. Create an OAuth App

    Open GitHub Settings → Developer settings → OAuth Apps → New OAuth App:

    Application name = CloudSSHHomepage URL = https://your-domain.comCallback URL = https://your-domain.com/api/auth/callback
  2. Save GitHub credentials

    Copy the Client ID, generate a Client Secret, and save it immediately—the complete secret is shown once.

  3. Configure the Worker
    GITHUB_CLIENT_ID = Client IDGITHUB_CLIENT_SECRET = Client SecretBASE_URL = https://your-domain.com
  4. Redeploy and verify

    The sign-in action appears automatically. Without OAuth, it stays hidden and anonymous SSH continues to work.

Credential boundary: saved passwords and keys use AES-256-GCM in each user's UserDBDO SQLite. One-click connections keep plaintext out of the browser and pass an internal one-time token.

06 / READ FIRST
Secrets, domains, and migrationsReview before upgrading an existing environment
Secrets

Dashboard: Worker → Settings → Variables and Secrets. CLI:

npx wrangler secret set <SECRET_NAME>
Custom domains

Bind separate production and test domains under Settings → Domains & Routes. The open-source wrangler.toml does not hard-code personal domains.

BASE_URL

When OAuth is enabled, it must exactly match the protocol and domain users visit or callback validation fails.

Durable Object migrations

Every new DO class needs a new, unique migration tag. Never delete a Worker during normal upgrades; only do so when intentionally rebuilding an environment with no data to retain.

Pre-release check

Connect production to main and test to test, using distinct Worker names and domains. Verify sign-in, SSH, SFTP, and migrations in test before production.

FEATURE_MATRIX

以下内容覆盖原完整 README 的全部核心特性，并按使用场景重新分组。

01
纯 TypeScript SSH-2.0

自研协议栈，不依赖第三方 SSH 库；全部加密操作基于 Web Crypto API。

02
多算法与双栈连接

支持 Curve25519-SHA256、ECDH-NISTP256、IPv4/IPv6，以及 OpenSSH 与 Dropbear。

03
密码与私钥认证

支持密码、Ed25519、ECDSA P-256/P-384/P-521 与 RSA-SHA2 私钥；旧 ssh-rsa 仅在显式兼容配置下启用。

04
TOFU 主机校验

首次显示 SHA-256 Host Key 指纹并持久化，后续连接检测指纹变化，降低中间人攻击风险。

05
WebGL 极客终端

xterm.js 与 WebGL 加速承载高频日志输出，支持多标签、搜索和完整历史日志导出。

06
可靠剪贴板交互

桌面端选区自动复制、右键粘贴；移动端显式选择模式。粘贴统一经过 xterm 输入管线并兼容 bracketed paste。

07
移动端深度适配

动态视口、安全区、软键盘、iOS IME、一次性 Ctrl/Alt、方向键与可选全屏横屏均经过专门处理。

08
Theme V2

五款内置主题覆盖明暗与赛博朋克风格；在线编辑并导出 JSON，登录用户导入后同步到账号，匿名用户保存在当前浏览器。

09
可视化 SFTP v3

目录浏览、上传下载、重命名、新建与删除；支持 Cmd/Ctrl 切换、Shift 连选、全选、批量队列与取消。

10
trzsz 原生传输

支持 trz/tsz、拖拽上传、目录传输、断点续传与 tmux；远端需安装 trzsz。

11
GitHub OAuth 与服务器管理

登录后可保存服务器、一键连接、按名称/主机/用户名搜索，并使用最多 10 个规范化标签筛选。

12
服务器系统自动识别

已保存服务器首次连接后通过独立 exec 通道后台读取 os-release 或 uname；成功结果持久化，unknown 不保存。

13
IP 隐私展示

IPv4/IPv6 在服务器列表和状态栏中视觉掩码，完整地址仍可快捷复制；掩码不等同于加密或访问控制。

14
隔离的多会话

一个页面并行管理多个终端、SFTP 与 Agent，每个标签的环境和上下文互相隔离。

15
安全匿名历史

最近 5 条匿名连接可选使用本地派生密钥进行 AES-256-GCM 加密后存入 localStorage。

16
双段延迟与 Colo

周期展示客户端至 Cloudflare 的 RTT、Cloudflare 至目标主机的连接延迟和当前数据中心代码。

17
智能区域调度

保存服务器时可通过 IPinfo 推断区域并持久化 locationHint；失败时回退 Cloudflare 默认调度，也可手动覆盖。

18
BYOK AI 运维助手

接入 OpenAI 兼容模型，提供命令执行、终端上下文、环境探测、进程、systemctl、Docker、确认和报告 8 个工具。

19
受控 AI 上下文与操作

终端选区仅作为非可信分析附件；安全命令可填入但不自动执行，危险命令需确认，禁止模式直接拒绝。

20
工程质量门禁

test/main 部署前执行冻结安装、类型检查、单元与集成测试、可复现构建、Playwright E2E 和 axe 无障碍回归。

端到端数据流

  1. 用户输入主机、账号和凭据，或选择 GitHub 账号中已保存的服务器。
  2. 浏览器通过 WebSocket 连接 Worker 与对应 SSHSessionDO。
  3. SSHSessionDO 使用 Cloudflare TCP Sockets 连接目标 SSH 服务。
  4. 执行版本交换、密钥交换、认证、打开通道、PTY 与 Shell 协商。
  5. 浏览器到 Worker 使用 WSS，Worker 到目标主机使用完整 SSH 加密。
  6. SFTP 在独立 SSH 子系统通道运行，不阻塞终端会话。
  7. 符合条件的已保存服务器在 Shell 就绪后通过独立 exec 通道后台识别 OS。
  8. Agent 将用户问题和非可信选区上下文交给外部 LLM，并只通过获准的 exec 操作返回流式结果。

Data flow

  1. Enter a host and credentials or select a saved server.
  2. The browser opens a WebSocket to the Worker and SSHSessionDO.
  3. The Durable Object opens a TCP Socket to the SSH service.
  4. SSH negotiates version, keys, authentication, channels, PTY, and shell.
  5. WSS protects browser-to-edge; SSH protects edge-to-host.
  6. SFTP uses an independent subsystem channel.
  7. Eligible saved servers run non-blocking OS detection over exec.
  8. The Agent sends user-approved operations through isolated exec channels.
